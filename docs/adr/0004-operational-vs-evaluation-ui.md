# 0004: Operational vs Evaluation UI

**Status**: Accepted
**Date**: 2026-07-21

## Context
The application supports both live operational awareness (using real providers like RailRadar) and offline/experimental evaluation (using the Evaluation Framework and SimulationProvider). We must prevent any risk of simulated or experimental data being mistaken for live, real-world operational state.

## Decision
Operational presentation and evaluation presentation are designated as fundamentally separate architectural concepts.

1. **Operational UI Responsibilities:** Consume live `AwarenessContext` and present actionable situational awareness to the end user. It must adhere strictly to display rules (no false precision, distinct confidence states).
2. **Evaluation UI Responsibilities:** Consume experimental `AwarenessContext` generated by simulated/evaluated runs, alongside evaluation metrics. It must clearly frame the data as an experiment.
3. **No Co-mingling:** Do NOT reuse `EmergencyMode.jsx` (or equivalent top-level operational entry points) for simulation or evaluation output. We will create a dedicated evaluation interface (e.g., `EvaluationReportView` or `SimulationDashboard`).
4. **Shared Rendering:** Shared UI components (like a generic progress bar or confidence badge) may be reused across both UIs, provided the macro-level views remain structurally and visually distinct.

## Alternatives Considered
- *Using a simple "Simulation Mode" flag in the existing Operational UI:* Rejected due to the high risk of user confusion. If the flag fails or is missed by the user, simulated data could be interpreted as live safety data.

## Consequences
- Requires the creation of entirely separate dashboard components for the Evaluation Framework in Phase 2/4.
- Reduces the risk of simulated data leaking into operational contexts.

## Affected Modules
- `client/src/components/EmergencyMode.jsx` (Kept strictly for operational use)
- Future `client/src/components/evaluation/*` (To be created)
